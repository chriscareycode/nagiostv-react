# NagiosTV Security Audit and Remediation Checklist — 2026-08-05

> The findings describe the application at the audited commit. The checklist below tracks remediation work in the current working tree. Checked items are implemented but are not considered deployed until they are included in a release and installed by operators.

## Executive summary

This source-level audit found **one critical, four high, three medium, and one low severity finding**. The one-click PHP updater is the most urgent issue: an attacker-controlled `version` query parameter is interpolated into shell commands, allowing command execution as the web-server user. The endpoint performs the update through a GET request and has no application-level authentication or CSRF protection.

The server settings writer, development proxy, unrestricted settings URL overrides, and storage of LLM API keys also create significant risk. In particular, a crafted NagiosTV link can override the LLM destination, unhide the LLM component, and cause monitoring data and a previously stored API key to be sent to an attacker-controlled server.

The dependency lockfiles were clean in `npm audit` on 2026-08-05. The principal risks are therefore first-party application and deployment behavior rather than known dependency advisories.

**Release recommendation:** do not expose `auto-version-switch.php` or `save-client-settings.php` until NTV-001 and NTV-002 are fixed. Remove both files from production artifacts by default. Do not expose the Node proxy outside a loopback-only development environment until NTV-004 is fixed.

## Scope and method

The review covered commit `8eb787ab6d22229dbf1f781b017c66c576ba6e13` and the following attack surfaces:

- React/TypeScript rendering, URL handling, persistence, data fetching, and LLM integration under `src/`
- The optional Express proxy under `node/`
- PHP connectors, update helpers, and shell scripts under `public/`
- Vite/build configuration, deployment guidance, dependency manifests, and lockfiles

The audit used manual data-flow review, targeted searches for injection and credential handling, JavaScript syntax validation, installed-tree inspection, and npm advisory checks. No requests were sent to a live Nagios server, and no exploit payload was executed.

PHP CLI was not available in the audit environment, so PHP syntax and runtime behavior were reviewed statically. Deployment-specific controls such as Apache authentication, TLS, response headers, network ACLs, and PHP configuration were not available for inspection. Those controls can reduce exposure but do not remove the application-layer defects described below.

## Detailed findings

### NTV-001 — Command injection and CSRF in the one-click updater

**Severity:** Critical
**Weaknesses:** CWE-78 (OS Command Injection), CWE-352 (Cross-Site Request Forgery), CWE-306 (Missing Authentication for Critical Function)

**Evidence**

- `public/auto-version-switch.php:53-68` accepts `$_GET['version']` and embeds it into a download URL without a strict version grammar.
- `public/auto-version-switch.php:70-71` applies `basename()` to the URL. This removes path components but does not neutralize shell metacharacters in the resulting filename.
- `public/auto-version-switch.php:103` and `:118` interpolate the derived filename and working directory into `shell_exec()` commands.
- The update is initiated by a GET (`src/hooks/useUpdateManager.ts:184-220`) and the PHP endpoint has no application-level authentication, authorization, CSRF token, or origin validation.
- Vite copies the PHP file into `build/auto-version-switch.php`, so the dangerous endpoint is included in production output.

**Impact**

An attacker who can request the endpoint can place shell syntax in `version` and execute commands with the privileges of the PHP/web-server account. The documented installation makes the application directory writable by that account (`README.md:90-97`), so compromise permits application replacement at minimum and may extend to Nagios data or host compromise depending on local permissions.

Outer Nagios HTTP authentication is not a complete mitigation. The endpoint is state-changing GET functionality and has no CSRF defense; a browser with cached Basic authentication or authenticated cookies may be induced to request it from another site. Deployments that follow the documented authentication-bypass option expose it directly.

The updater also installs a release archive without checking a pinned digest or signature, increasing supply-chain impact if the release channel is compromised.

**Remediation**

1. Immediately exclude this endpoint from builds/releases and remove or deny access to it on deployed systems.
2. Replace shell-based extraction/copying with APIs that do not invoke a shell. If a process must be launched, pass arguments as an array and never concatenate user input into a command.
3. Accept only a strict, anchored release identifier (for example, a SemVer parser or a conservative allowlist) and resolve it against release metadata controlled by the server. Do not accept arbitrary versions directly from the request.
4. Require explicit administrator authorization, use POST, validate a per-session CSRF token and request origin, and reject every other method.
5. Download into a unique non-web-accessible directory, reject symlinks/path traversal in archives, verify a publisher signature or pinned SHA-256 digest, and perform an atomic deployment with rollback.

### NTV-002 — Unauthenticated/CSRF-prone server settings overwrite and truncation

**Severity:** High
**Weaknesses:** CWE-306 (Missing Authentication for Critical Function), CWE-352 (Cross-Site Request Forgery), CWE-400 (Uncontrolled Resource Consumption)

**Evidence**

- `public/save-client-settings.php:21-34` writes the raw request body to `client-settings.json` with no authentication, authorization, CSRF protection, content-type check, schema validation, or size limit.
- The file is opened with mode `w` for every request. A GET or any non-POST request therefore truncates the settings file to zero bytes.
- `src/components/settings/SettingsPersistence.tsx:22-35` invokes the endpoint directly and provides no anti-CSRF token.
- The UI recommends making the file world-writable (`src/components/settings/SettingsPersistence.tsx:76-83`); the README presents `chmod 777` as an alternative (`README.md:68-80`).
- Vite copies the writer into `build/save-client-settings.php`.

**Impact**

Any client able to reach the endpoint can erase or replace shared application configuration. A cross-site request can perform the write even when the browser cannot read the response. Malicious settings can redirect data flows, enable NTV-005, degrade polling performance, or present misleading dashboard content. Concurrent writes can corrupt the file, and an unbounded body can consume disk space.

**Remediation**

1. Exclude the endpoint from production artifacts by default. Prefer administrator-managed configuration outside the web root.
2. If browser-based administration is retained, require authenticated administrator authorization, POST only, a CSRF token, same-origin validation, JSON content type, a small body limit, and strict runtime validation against an explicit settings schema.
3. Write to a temporary file with restrictive permissions and atomically rename it after validation and `fsync`; serialize concurrent updates.
4. Run the application with least privilege and never require `0777`. Make only the specific configuration file writable by a dedicated service identity.

### NTV-003 — LLM API keys are stored in publicly readable settings and script-readable browser storage

**Severity:** High
**Weaknesses:** CWE-312 (Cleartext Storage of Sensitive Information), CWE-922 (Insecure Storage of Sensitive Information)

**Evidence**

- `llmApiKey` is part of the general `ClientSettings` object (`src/types/settings.ts:116-126`).
- Saving locally serializes the entire object to `localStorage`, with a JavaScript-readable cookie fallback (`src/helpers/persistence.ts:77-94` and `:128-134`). The fallback cookie does not set `Secure` or an explicit `SameSite` policy and cannot be `HttpOnly` because JavaScript reads it.
- Saving to the server posts the entire settings object (`src/components/settings/SettingsPersistence.tsx:22-27`). The server writes it to `client-settings.json` (`public/save-client-settings.php:27-30`).
- Every client fetches that same static JSON file without access segregation (`src/components/SettingsLoad.tsx:120-139`). Thus any API key in server settings is intentionally delivered to all dashboard users and is ordinarily retrievable as a static resource.
- The “Show JSON” and clipboard actions serialize the key along with non-sensitive preferences (`src/components/settings/SettingsPersistence.tsx:37-39` and `:95-115`).

**Impact**

An LLM provider credential may be exposed to every dashboard user, anyone able to retrieve the static settings file, injected same-origin script, browser extensions, shared-browser users, backups, screenshots, or clipboard history. A stolen key can incur cost and expose provider-side data. NTV-005 provides a direct path for a crafted link to send an already stored key to an attacker.

**Remediation**

1. Remove secrets from `ClientSettings`, URL overrides, exported JSON, clipboard output, and browser persistence.
2. Keep provider credentials in a server-side secret store and expose a narrow same-origin LLM relay with user authorization, destination allowlisting, request limits, and audit logging.
3. If a browser-supplied key must be supported, keep it in memory for the current tab only, clearly warn the user, never include it in shared server settings, and provide an explicit purge control.
4. Treat any key previously saved to `client-settings.json` as exposed and rotate it after remediation.

### NTV-004 — Development proxy delegates Nagios credentials to unauthenticated clients and disables TLS verification

**Severity:** High
**Weaknesses:** CWE-306 (Missing Authentication for Critical Function), CWE-295 (Improper Certificate Validation)

**Evidence**

- `node/app.js:58` enables CORS for all origins.
- `node/app.js:74-103` exposes a GET proxy with no client authentication or authorization.
- When configured, the proxy adds a privileged Basic `Authorization` header to every proxied request (`node/app.js:94-101`).
- `node/app.js:88-91` sets `rejectUnauthorized = false`, disabling certificate verification for an HTTPS upstream and exposing the Basic credential and monitoring data to man-in-the-middle attack.
- `node/app.js:109-110` listens without a host restriction; Node therefore normally binds on all available interfaces rather than loopback only.

**Impact**

Any client that can reach the proxy can use its stored Nagios credential to query allowed Nagios CGI resources. Permissive CORS lets an arbitrary website drive and read those requests from a visitor's browser. If HTTPS is used upstream, an on-path attacker can impersonate Nagios and capture the Basic credential because certificate validation is disabled.

The proxy is documented as development-only, which reduces intended exposure but not the risk of its default network behavior.

**Remediation**

1. Bind to `127.0.0.1` by default and fail closed unless an operator explicitly enables another interface.
2. Remove wildcard CORS; allow only an exact configured development origin.
3. Require client authentication/authorization if non-loopback access is supported, and narrowly allowlist CGI resource names and query parameters.
4. Restore TLS certificate and hostname validation. Support a configured private CA bundle when Nagios uses an internal CA.
5. Store proxy credentials outside executable JavaScript configuration with restrictive filesystem permissions and never log them.

### NTV-005 — URL overrides can exfiltrate monitoring data and stored LLM credentials

**Severity:** High
**Weakness:** CWE-15 (External Control of System or Configuration Setting)

**Evidence**

- `src/helpers/settingsUrl.ts:45-85` accepts every property present in `clientSettingsInitial` from either the query string or hash, including `hideLocalLLMSection`, `llmServerBaseUrl`, `llmBackendType`, and `llmApiKey`.
- URL values are applied after remote and local settings (`src/components/SettingsLoad.tsx:55-69`, `:85-110`, and `:150-164`), so they override a user's stored configuration.
- Setting `hideLocalLLMSection=false` mounts the component (`src/components/Dashboard.tsx:73-74`). It automatically performs analysis after five seconds (`src/hooks/useLlmAnalysisController.ts:193-209`).
- The analysis sends filtered hosts, services, and alerts to the configured URL and attaches the configured API key (`src/hooks/useLlmAnalysisController.ts:74-99`; `src/helpers/llmBackends.ts:74-99` and `:239-247`).

**Impact**

An attacker can send a crafted NagiosTV link that enables the LLM and points it at an attacker-controlled CORS-enabled endpoint. When an authenticated operator opens the link, the application automatically sends monitoring inventory/status data. If the browser already contains an LLM key, that key is also attached to the attacker-controlled request unless explicitly replaced in the URL.

**Remediation**

1. Replace the “all known settings” URL behavior with a small explicit allowlist of presentation-only, non-sensitive options.
2. Never allow URLs to override endpoints, credentials, data sources, prompts, automatic network actions, or `serverSettingsTakePrecedence`.
3. Validate endpoint URLs with the `URL` API, require HTTPS except for explicit loopback development, and allowlist trusted hosts.
4. Do not automatically transmit monitoring data after a configuration change. Require an explicit user action that displays the destination and the categories of data to be sent.
5. Add regression tests proving security-sensitive properties are ignored in both normal-query and hash-query overrides.

### NTV-006 — Livestatus exposes monitoring data with origin-reflecting CORS and no application authorization

**Severity:** Medium
**Weaknesses:** CWE-942 (Permissive Cross-domain Policy with Untrusted Domains), CWE-306 (Missing Authentication for Critical Function)

**Evidence**

- `public/connectors/livestatus.php:199-202` reflects any supplied `Origin` into `Access-Control-Allow-Origin` without an allowlist or `Vary: Origin`.
- The connector contains no application-level authentication or authorization before querying the local Livestatus socket.
- Host, service, alert, group, comment, and program-status queries return internal monitoring information.

**Impact**

If outer web-server authentication or network controls are missing or intentionally bypassed, any reachable client can retrieve infrastructure names, service states, plugin output, comments, and alert history. The CORS policy additionally allows arbitrary websites to read that data through a visitor's browser where browser/network policy permits the request. Reflected responses can also be served to the wrong origin by caches that do not vary on `Origin`.

**Remediation**

Require authentication and read authorization at the endpoint or its reverse proxy, restrict it to the dashboard's exact origin, add `Vary: Origin`, and deny access by default. If cross-origin access is unnecessary, remove the CORS header entirely. Keep the connector reachable only from trusted networks and return generic errors that do not include raw queries.

### NTV-007 — Configurable external links retain `window.opener` and accept unsafe destinations

**Severity:** Medium
**Weakness:** CWE-1022 (Use of Web Link to Untrusted Target with `window.opener` Access)

**Evidence**

- Host, service, and alert items construct a URL from unrestricted `externalLinkBaseUrl` and open it with `window.open(url, '_blank')` (`src/components/hosts/HostItem.tsx:100-104`, `src/components/services/ServiceItem.tsx:110-124`, and `src/components/alerts/AlertItem.tsx:58-83`).
- No scheme/host validation is applied, and programmatic new windows are not opened with `noopener` or followed by `win.opener = null`.
- NTV-005's broad URL override behavior lets a crafted link choose `externalLinkBaseUrl` for the session.
- `encodeURI()` is used on the complete string rather than constructing query parameters with `URLSearchParams`, so reserved characters in host/service values remain structurally significant.

**Impact**

After a user clicks an external-link icon, an attacker-controlled destination can retain a reference to the NagiosTV window and navigate it to a phishing page (reverse tabnabbing). The destination also receives host/service names in its query string. Unsafe schemes are not rejected.

**Remediation**

Parse with `new URL()`, require `http:` or `https:`, and enforce an administrator-defined origin allowlist. Construct query parameters with `URLSearchParams`. Open with the `noopener,noreferrer` features and explicitly set `opener` to `null` as a compatibility fallback. Remove this field from URL overrides.

### NTV-008 — Production security headers and HTTPS requirements are not defined

**Severity:** Medium
**Weaknesses:** CWE-693 (Protection Mechanism Failure), CWE-319 (Cleartext Transmission of Sensitive Information)

**Evidence**

- No Content Security Policy, `frame-ancestors`/`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, or HSTS policy is defined in repository deployment configuration or `index.html`.
- Installation examples use plain HTTP (`README.md:64`), and the sample Node proxy advertises HTTP (`node/app.js:117-119`).
- The application displays sensitive monitoring data and may handle LLM API keys.

**Impact**

Missing headers increase the impact of a future injection bug, allow framing/clickjacking unless the outer Nagios configuration prevents it, and may leak full navigation URLs through referrers. Plain HTTP permits interception and modification of monitoring data, settings, and authentication traffic.

**Remediation**

Publish a supported Apache/reverse-proxy configuration that redirects HTTP to HTTPS and sets, at minimum:

- a tested CSP with `default-src 'self'`, a restrictive `connect-src` derived from configured Nagios/LLM endpoints, `object-src 'none'`, and `frame-ancestors 'self'` (or `'none'` if framing is not needed);
- `X-Content-Type-Options: nosniff`;
- `Referrer-Policy: no-referrer` or `strict-origin-when-cross-origin`;
- a narrowly scoped `Permissions-Policy`;
- HSTS after HTTPS is consistently deployed.

Avoid relying on a CSP meta tag when server headers are available; framing and HSTS protections require HTTP response headers.

### NTV-009 — Update probe discloses filesystem path and service account name

**Severity:** Low
**Weakness:** CWE-200 (Exposure of Sensitive Information)

**Evidence**

- `public/auto-version-switch.php:38-51` executes `whoami` and returns both the absolute script directory and operating-system account name from `?testphp=true`.
- The response reflects arbitrary origins into `Access-Control-Allow-Origin`.

**Impact**

The information improves attacker reconnaissance and makes command-injection payloads easier to tailor. It is especially harmful in combination with NTV-001.

**Remediation**

Remove the probe from production. A health endpoint should return only a boolean capability/status value, require administrative authorization, and never expose local paths or account names.

## Positive observations

- React renders Nagios host, service, plugin-output, comment, and LLM text as text nodes. The custom LLM markdown renderer also builds React elements instead of using `dangerouslySetInnerHTML`, substantially reducing stored-XSS risk from monitoring or model output.
- External links written as JSX anchors consistently use `rel="noopener noreferrer"`; the gap is limited to the programmatic `window.open()` paths described in NTV-007.
- Nagios query parameters are generally built with `URLSearchParams` in `src/helpers/nagiosUrls.ts`.
- Sensitive local proxy configuration files (`node/settings.js` and `node/settings-nagios.js`) and `public/client-settings.json` are gitignored, and the tracked tree contained no private-key or common provider-token signatures in the targeted scan.
- The production frontend and proxy lockfiles reported zero known vulnerabilities in npm's advisory database on 2026-08-05.

## Recommended remediation order

1. Remove/deny production access to both PHP mutation endpoints; fix NTV-001 before any further release.
2. Rotate any LLM key ever written to a shared `client-settings.json`, then separate secrets from client settings.
3. Restrict URL overrides to presentation-only fields and prevent automatic transmission to changed LLM destinations.
4. Bind and authenticate the proxy, restrict CORS, and restore upstream TLS validation.
5. Protect Livestatus and external navigation, then ship a hardened HTTPS/header configuration.
6. Add security regression tests for updater input validation, method/auth/CSRF enforcement, settings schema and size limits, sensitive URL-override rejection, and destination allowlisting.
